fix(storage): 存储写入失败不再静默 v1.24.5

把 localStorage 的每个写入点按「本次写失败，用户会不会以为已经保存了」
过了一遍，修掉三处会让数据无声消失的地方：

1. persistMeta（本地纠错：中文名/原名/作者/别名/出版社/发售日）
   catch 是 `/* 隐私模式下忽略 */`。详情页立刻显示改后的值（改的是
   内存对象），刷新全没，且要一条条重打。

2. persistDrafts（书评草稿）同样静默，且连 canStore 判断都没有，
   而界面上一直写着「草稿已自动保存」，用户写十几分钟的笔记关掉详情
   就没了。

3. persistDeleted（删除墓碑）写失败后，删掉的书会在下次云同步时被
   远端数据重新合并进来。不是「删不掉」，是「过一会儿自己回来了」。

第一版修复是假修复：在 catch 里 toast 一句失败文案，验收全绿。但调用
方紧接的一两行就是 toast('已保存本地纠错') / toast('已标记为「读完」')，
而 toast 是单例元素，失败提示在同一帧内被覆盖，用户从头到尾只看得到
「已保存」。改用顶部常驻横幅 #storageWarn 做主通道，toast 只做补充且
全局只弹一次（一次操作常连写两三个 key，每个都弹会刷屏）。

横幅按 key 粒度记账：纠错写失败、紧接着收藏写成功时不能撤横幅——
「另一个 key 写成功」不代表丢的数据回来了。isQuotaError() 分流「配额满
（清理即可）」与「真被禁用（隐私模式）」，原来一律说「浏览器禁止本地
存储」，配额满时用户会去翻一个根本不存在的开关。草稿提示同步改为
「· 草稿未能保存」。

其余 8 处写入点（SETTINGS/PREFS/HIST/GOAL/DAYS/GIST/SYNCLOG/VIEWS）
评估后有意保留静默：丢的是可重建的派生状态，界面会当场回落，且写入
高频——接横幅会在配额满时持续刷提示，把真正的丢失信号淹掉。判断标准：
写入内容是不是用户手打、且界面会显示「已保存」。
